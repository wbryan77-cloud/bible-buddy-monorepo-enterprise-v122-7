# BibleBuddy Enterprise Handbook

## Current Direction
Feature development is temporarily frozen except for stabilization, consolidation, testing, observability, and migration work.

## Mission
BibleBuddy must become one calm, trustworthy, Scripture-first companion with one consistent voice.

## Core Principle
Conversation owns the relationship.
Turn Intent owns understanding.
Continuation owns conversation.
Scripture owns truth.
AI assists composition.
Scripture validates doctrine.
One companion speaks.
Enterprise architecture protects everything.

## Five Permanent Layers
1. Constitution and Governance
2. Conversation Engine
3. Companion Intelligence
4. Bible Intelligence
5. Companion Composer
6. Platform and Scale

## Five Gates
No new feature, route, owner, helper, runtime, AI tool, memory engine, doctrine pack, or UI component enters unless it answers YES to all:

1. Does it simplify the architecture?
2. Does it strengthen the Companion Core?
3. Does it preserve Scripture as final authority while keeping one voice?
4. Does it follow enterprise/industry-standard architecture?
5. Does it review and learn from prior BibleBuddy audits, coding mistakes, regressions, route conflicts, and fixes?

## Stabilization Order
1. Consolidate architecture.
2. Observe current runtime behavior.
3. Migrate one legacy owner at a time.
4. Retire legacy ownership only after regression proof.
5. Strengthen deployment discipline.
6. Resume features only after the foundation is stable.

## Bible-First Rule
BibleBuddy never teaches doctrine because AI thinks it is true.
BibleBuddy teaches only where Scripture supports it.

Genesis to Revelation.
Line upon line.
Precept upon precept.
Scripture interprets Scripture.

## Anti-Drift Rule
Do not add another owner to solve an owner conflict.
Do not add another route to solve route sprawl.
Do not add another file unless it replaces complexity, documents permanent architecture, or protects production.


## Historical Learning

BibleBuddy must learn from its own history.

Before any architectural change:

- Review previous audits.
- Review previous regressions.
- Review previous production issues.
- Review previous route conflicts.
- Review previous architecture decisions.
- Prefer replacing complexity over adding complexity.
- Never introduce a new owner to solve an owner conflict.
- Never introduce a new route to solve route sprawl.
- Retire technical debt whenever practical.
- Preserve lessons learned so future development does not repeat past mistakes.

Historical learning is a permanent enterprise engineering requirement.
